# 방법론

_[English](METHODOLOGY.md) · 영문 문서가 기준입니다._

이 문서는 출력을 어떻게 읽어야 하는지와, 구현된 `RAPID_PRICE_LIFT` 버전 `1.1`
규칙을 정의합니다.

## 질문과 결과 어휘

첫 적용 사례가 묻는 것은, 짧은 구간의 가격 상승이 반복적이고 집중된 적극 매수의
선언된 패턴을 충족하는가입니다.

재현 결과는 일부러 닫아 두었습니다.

| 결과            | 뜻                                                                              |
| --------------- | ------------------------------------------------------------------------------- |
| `SUPPORTED`     | 검증된 자료가 승인된 규칙 버전의 필수 기준값을 모두 충족합니다.                 |
| `NOT_SUPPORTED` | 자료는 충분하지만, 필수 기준값 가운데 하나 이상을 충족하지 못합니다.            |
| `INCONCLUSIVE`  | 승인된 입력이 규칙까지 도달했지만, 비교에 쓸 유효한 증거가 충분하지 않았습니다. |

이 상태들은 기술적인 패턴 가설에 대한 것입니다. 법적 결론도 인과에 대한 결론도
아닙니다.

재현 전에 발견되는 입력 식별자, 항목 연결, 조사 범위, 매개변수, 승인의 모호함은
언제나 `REVIEW_REQUIRED`이며 `INCONCLUSIVE`가 아닙니다. 코드가 소유한 상태
표는 허용되지 않은 전이를 현재 상태를 바꾸지 않은 채 거부합니다. 모든 HTTP
요청은 `UPLOADED`에서 시작하고, 항목 연결·입력·사례 관문이 `applyTransition`을
통해 요청 안에서만 유효한 전이를 실행합니다. 실패한 관문은 이슈 코드에서 상태를
유추하지 않고 `MAPPING_REVIEW_REQUIRED`, `INPUT_REVIEW_REQUIRED`,
`CASE_REVIEW_REQUIRED` 가운데 하나를 그대로 돌려줍니다. 승인 관문은 필요한 승인
기록이 각자의 아티팩트 해시와 일치하지 않으면 재현 해시를 만들지 않습니다.

픽스처 재현 HTTP 경계도 같은 구분을 적용합니다. 이름이 붙은 커밋된 CSV 또는
JSON Lines 시나리오, 닫힌 변형, 최대 64개의 선언된 원본 행, 항목 연결 승인
기록, 그리고 선택적인 승인된 사례 매니페스트를 검증합니다. 호출자가 작성한 정본
이벤트는 결코 받지 않습니다. API는 자신이 실행한 버전 있는 제안을 직접 해싱하고,
승인과 사유가 적힌 항목 재정의를 확인하고, 모든 행이 승인된 원본 아티팩트에
속하는지 확인하고, 같은 좌표에 있는 서버 소유의 커밋된 행과 값을 비교한 뒤에야
승인된 항목 연결을 통해 이벤트를 다시 만듭니다. 엔진은 또한 커밋된 아티팩트가
선언한 모든 행 번호가 제출되었는지, 제출된 모든 행이 승인된 항목 연결이 선언한
모든 원본 열을 담고 있는지 확인합니다. 행이 빠지면 `SOURCE_ROW_MISSING`,
열 키가 없으면 `APPROVED_SOURCE_COLUMN_MISSING`을 돌려줍니다. 키가 있고 값이 빈
문자열이면 기존의 변환과 목표 항목 검증을 그대로 받습니다. 값이 다르면
`SOURCE_ROW_MISMATCH`로 거부합니다. 어떤 실패든 구조화된 `REVIEW_REQUIRED`를
HTTP `422`와 함께, 조치 가능한 경로와 최종 진행 상태를 담아 돌려주며 재현 해시는
담지 않습니다.

성공 응답은 계약으로 검증된 재현 결과의 투영입니다. 엔진 버전, 개수, 정본 순서
식별자, 결과 해시를 드러냅니다. 평가된 사례의 응답은 버전이 붙은
`sourceTrace`도 함께 드러냅니다. 각각의 서로 다른 발견 이벤트는 허용 목록에 있는
정본 이벤트와 그 `rawRowHash`, 그리고 정확한 커밋 원본 행으로 이어집니다. 항목
연결까지만 검증하면 `MAPPING_APPROVED`에서 끝나며 기존의 정본 결과를
돌려줍니다. 승인된 항목 연결과 사례 매니페스트를 갖춘 재현만이 `REPLAYED`로
끝납니다. 응답의 진행 상태는 정본 결과 해시의 입력이 아니며, 원본 추적도
아닙니다.

평가된 모든 판단 항목은, 충족하지 못한 항목까지 포함해, 사례 재현 화면에서
읽기 전용 원본 확인을 제공합니다. 서버가 보관된 원본 행 해시를 커밋된 좌표와
그대로인 문자열 값에 연결하고, 브라우저는 그렇게 해석된 증거를 보여 주기만
합니다. 아티팩트 이름, 아티팩트 해시, 물리적 원본 행 번호가 요청 배열의 순서와
무관하게 기록을 식별합니다. 원래의 공백, 소수 표기, 연결하지 않은 열은
이스케이프된 텍스트로 그대로 보입니다. 같은 판단 항목을 여러 번 참조하면 추적
항목 하나를 공유하고, 완전한 중복 이벤트는 정본 이벤트 하나로 합쳐집니다. 서버가
소유한 연결이 없거나 모호하면 내부 오류입니다.

`INCONCLUSIVE` 응답에는 발견도 원본 증거도 없습니다. 발견 없는 개수만으로 대체
행을 가져오지 않습니다. 입력이나 승인이 바뀌거나, 새로 실행하거나, 실패하면 이전
증거를 지웁니다. 지나간 요청이 새 선택을 다시 채울 수 없습니다. 이 추적은 합성
원본 기록까지의 출처를 세울 뿐, 인과나 법적 결론을 세우지 않습니다. 증거 번들의
조립, 내보내기, 독립 검증은 아직 계획 단계입니다.

진행 상태는 요청 하나의 수명 동안에만 존재합니다. `INPUT_REVIEW_REQUIRED`
응답 이후 입력을 고치면 `UPLOADED`에서 새 실행이 시작되며, 영속화와 요청 간
진행 이력은 구현되어 있지 않습니다.

## 데이터셋 프로파일과 승인 범위

정본 이벤트는 정본 데이터셋 해시, 정렬된 고유 종목·거래 주체 식별자, 정규화된
최초·최종 시각을 결정론적으로 만들어 냅니다. 사례 검증은 그 `DatasetProfile`만
받습니다. 데이터셋 해시가 다르거나, 선언된 종목이나 거래 주체가 없거나, 구간이
프로파일 밖이면 재현 전에 멈춥니다. `1.4` 선언에서 없는 종목은 각각
`hypothesis.instrumentIds[index]` 경로에 보고됩니다.

사례 매니페스트 `1.3`은 `RAPID_PRICE_LIFT`를 위한 엄격한 단일 종목 형태로 남아
있고 여전히 거래 주체를 요구합니다. 나란히 있는 엄격한 `1.4` 스키마는 비어 있지
않은 `instrumentIds` 집합을 선언하고, 닫힌 패턴 어휘 `RAPID_PRICE_LIFT`와
`CROSS_MARKET_SESSION_REVERSAL`을 씁니다. 계약 정책은 빠른 가격 상승에 대해
여전히 거래 주체를 요구하지만, 교차시장 세션 되돌림에 대해서는
`actorIds: []`를 허용합니다. 빈 목록은 원본에 거래 주체 식별자가 없다는 기록이며,
아무도 거래하지 않았다는 주장이 아닙니다. 정본 데이터셋 프로파일에 거래 주체가
하나라도 있으면 프로파일 검증이 그 선언을 거부합니다. 거래 주체가 없는 선언은
아래에서 설명하는, 따로 버전이 붙은 교차시장 세션 되돌림 규칙이 사용합니다.

사례 매니페스트는 쓸 수 있는 승인 상태 대신 승인 기록을 가집니다. 항목 연결
승인은 별도의 기록을 씁니다. 두 기록 모두 불투명한 검토자 참조, 결정, 승인 시각,
사유가 적힌 재정의 경로를 유지하면서 변경 불가능한 제안 아티팩트에 묶입니다.
선언된 픽스처 기준값 `1.0`보다 낮은 항목 연결 확신도나 `REVIEW_REQUIRED` 항목은
그에 대응하는 재정의와 빈칸이 아닌 사유를 요구합니다. 재현 서비스 경계에서
해소되지 않은 표시 항목은 해당 항목 경로에 `MAPPING_OVERRIDE_REQUIRED`를
돌려줍니다. 응답 계약에는 시나리오 수준의 `MAPPING_REVIEW_REQUIRED` 코드가 더
이상 없습니다. 같은 이름의 진행 상태는 그대로입니다.

`RAPID_PRICE_LIFT` `1.1` 레지스트리는 가격 변화, 적극 매수 비중, 거래 주체 집중,
기준가 초과 체결, 제거 민감도에 대해 선언된 매개변수 이름만 받습니다. 값은
소수 또는 부호 없는 정수 문자열입니다. 레지스트리는 값도, 기본값도, 대체값도
제공하지 않습니다. 규칙 평가에는 일치하는 `RAPID_PRICE_LIFT` `1.1` 설정이 정확히
하나 필요하며, 없거나 여럿이면 평가 전에 `RULE_CONFIGURATION_REQUIRED`를
돌려줍니다. 현재 계약은 버전 `1.0`을 거부합니다. 새로운 적격성 의미를 쓰려면
매니페스트를 `1.1`로 옮기고, 승인 아티팩트 해시를 다시 계산하고, 새로 승인을
받아야 합니다. 기존 `1.0` 증거는 원래의 버전 표시를 유지하며 이 런타임이 다시
해석하지 않습니다.

## 정본 시각과 순서

구현된 기반은 네 자리 ISO 달력 연도, 대문자 `T`, `Z` 또는 명시적인 `±HH:MM`
오프셋, 그리고 최대 아홉 자리의 소수 자릿수를 가진 `eventTime` 값을 받습니다.
월은 `01`부터 `12`까지이고, 일은 선행 그레고리력 윤년 규칙에 따라 그 달에 실제로
존재해야 하며, 시는 `00`부터 `23`까지, 분과 초는 `00`부터 `59`까지입니다. 오프셋
시는 `00`부터 `23`까지, 오프셋 분은 `00`부터 `59`까지입니다. 윤초는 지원하지
않습니다. 정렬이나 해싱 전에, 엔진은 허용된 값을 고정 폭 UTC 나노초로
변환합니다.

```text
YYYY-MM-DDTHH:mm:ss.sssssssssZ
```

UTC 결과는 `0000`년부터 `9999`년 사이에 있어야 합니다. 이벤트 시각은 밀리초 단위
날짜 파싱이 아니라 부호 있는 나노초 정수로 비교합니다. 시각이 같은 이벤트는 부호
없는 수치 `sequence` 비교를 거친 뒤 UTF-16 코드 단위 사전순 `eventId` 순서를
따릅니다. 정본 JSON 키도 같은 코드 단위 순서를 쓰며, 호스트의 로케일 자료나 객체
속성 열거 순서에 의존하지 않습니다.

유한 JSON 수의 표기는 런타임이 이미 가지고 있는 IEEE 754 binary64 값에 대해
RFC 8785 3.2.2.3절을 따릅니다. 왕복 가능한 가장 짧은 ECMAScript 표현을 쓰므로
음의 0은 `0`이 되고, `1e-6`은 `0.000001`, `1e-7`은 `1e-7`, `1e20`은
`100000000000000000000`, `1e21`은 `1e+21`이 됩니다. 지수는 소문자 `e`를 쓰고
필요하면 `+`를 포함합니다. `0.1`, 가장 작은 양의 비정규 수, 가장 큰 유한 수는
각각 `0.1`, `5e-324`, `1.7976931348623157e+308`으로 직렬화됩니다. `NaN`과 두 무한
값은 거부됩니다. JSON 수는 정본화 전에 이미 binary64로 반올림되어 있으므로,
직렬화가 잃어버린 정밀도를 되살릴 수는 없습니다. 그래서 정확한 가격, 수량, 금액,
금융 비율, 기준값은 소수 문자열로 남고 확대된 정수 연산을 씁니다.

Trade Event `1.1`은 검증 시점에 가격과 수량 문자열을 정본화합니다. 허용되는
문법에서 지수 표기, `+` 접두사, 앞자리 0, 로케일 형식, 유한하지 않은 값은
제외됩니다. 의미 없는 소수점 이하 0은 제거되고, `-0`, `-0.0`을 비롯해 허용되는
음의 0 표기는 `0`이 됩니다. 이는 원본 식별자별 묶기, 중복 분류, 투영, 해싱보다
앞서 수행되는 문자열 연산이며, 규칙의 확대 정수 연산을 바꾸지 않습니다.

이것은 RFC 8785의 유한 수 규칙에 한정된 것이지 JSON Canonicalization Scheme을
완전히 준수한다는 주장이 아닙니다. 기존의 UTF-16 키 순서와 `undefined` 정책은
그대로입니다. 값이 `undefined`인 객체 속성은 생략하고, 배열 안의 `undefined`나
빈 자리는 거부합니다.

현재의 데이터셋 계약은 순서가 있는 하나의 원본 흐름을 나타냅니다. 모든 이벤트는
`sequence`를 제공하거나 모두 생략해야 하며, 섞여 있으면
`MIXED_SEQUENCE_PRESENCE`로 재현이 멈춥니다. 모든 이벤트가 시퀀스를 생략하면
시각이 같은 이벤트는 `eventId`로 넘어갑니다. 완전한 중복을 합친 뒤에는 정본
`eventId`가 원본 식별자들 사이에서 고유해야 전체 순서의 결정자로 쓰일 수
있습니다. 없는 시퀀스를 추정하거나, 정본화 과정에서 대체 식별자를 만들거나,
식별자를 유니코드 정규화하지 않습니다.

## 원본 식별자, 중복, 해시 범위

구현된 원본 식별자는 `datasetId`, `venueId`, `sourceEventId`의 조합입니다. 검증과
시각 정규화 뒤에 엔진은 정렬 전에 그 식별자로 이벤트를 묶습니다. 반복된 기록은
정본 투영이 같을 때만 합쳐지고, `duplicateCount`가 몇 개를 제거했는지
기록합니다. 한 식별자에 서로 다른 정본 투영이 있으면 재현 전에
`CONFLICTING_SOURCE_IDENTITY`로 정본화가 실패하고 결과 해시는 생기지 않습니다.
서로 다른 원본 식별자가 같은 정본 `eventId`를 가지면, 중복을 합친 뒤 정렬과 해싱
전에 `CONFLICTING_EVENT_IDENTIFIER`로 실패합니다. 두 실패 모두 입력 순서와
무관하게 정본 키 순서로 첫 충돌을 고르며, `INCONCLUSIVE` 규칙 결과 대신 검토를
요구합니다.

정본 이벤트 투영은 의미 있는 항목의 명시적 허용 목록입니다. `schemaVersion`,
`eventId`, `sourceEventId`, `datasetId`, `venueId`, `eventTime`, `sequence`,
`instrumentId`, `eventType`, `side`, `actorId`, `counterpartyId`, `orderId`,
`price`, `quantity`입니다. 수집 메타데이터인 `receivedAt`과 `rawRowHash`는 조사에
쓰이도록 반환 이벤트에 남지만 기록 동등성과 정본 결과 해시 밖에 있습니다.
스키마 포괄 시험이 모든 `TradeEvent` 항목을 명시적으로 분류하도록 요구해서,
스키마에 항목을 더하는 것만으로 보호 범위가 조용히 넓어지거나 우회되지 않게
합니다.

## 원본 출처와 승인된 항목 연결

구현된 반입 경로는 아티팩트의 정확한 바이트를 `sourceArtifactHash`로 해싱합니다.
각 원본 행은 아티팩트 해시와 행 번호로 이루어진 좌표, 그리고 문자열 값 그대로를
담은 정본 JSON으로 직렬화된 뒤 `rawRowHash`로 해싱됩니다. 승인된 항목 연결은
닫힌 변환만 적용합니다. 승인되지 않은 열, 중복된 원본이나 목표 연결, 알 수 없는
변환, 거부된 값, 없는 승인 열, 없는 필수 목표, 중복 좌표, 아티팩트 불일치는 정본
데이터셋이나 결과 해싱 전에 멈춥니다. 커밋된 시나리오의 행 배열은 CSV와 JSON
Lines 아티팩트 파서의 완전한 출력에 시험으로 고정되어 있습니다. 순서 섞기 조작은
파싱된 이 기록들을 승인된 항목 연결에 제출하기 전에 재배열합니다. 재현은 선언된
행의 완전성과 좌표를 확인한 뒤, 제출된 순서 그대로 연결하며 서버에서 추가로
섞지 않습니다. 중복 조작은 대신 항목 연결 후 처음 파생된 이벤트를 반복합니다.
완전히 같은 이벤트의 중복 제거는 명시적인 중복 개수와 함께 의미상의 결과를
유지합니다. 원본 좌표가 실제로 반복되면 결과나 원본 추적 없이 HTTP `422` /
`INPUT_REVIEW_REQUIRED`를 돌려줍니다.

시험되는 경계는 고정된 커밋 CSV/JSON Lines 바이트 → 파싱된 행 기록 → 제출된
순열 → 승인된 항목 연결 → 정본 재현입니다. 두 형식과 세 규칙 사례의 대표적인
순열이 정본 순서와 결과 해시 문자열을 그대로 유지하고, 규칙 사례에서는 평가와
원본 추적도 유지됩니다. 이 점검은 파일 바이트를 다시 쓰거나, 좌표에 새 번호를
매기거나, 출처가 새로운 임의의 원본 파일 순열에 대한 불변성을 세우지 않습니다.
커밋된 파서, 재현 경로, 승인 경계 시험은 `pnpm test`로 실행합니다. 브라우저 보조
코드의 주입된 난수는 순열의 다양성과 제한된 대체 경로를 시험하는 데만 쓰이며,
난수가 승인이나 금융 연산, 해시에 들어가는 일은 없습니다.

정본 `eventId`는 퍼센트 인코딩된 조합
`event:<datasetId>:<venueId>:<sourceEventId>`로 만들어집니다. 엔진은 정규화된
정본 투영을 정렬해 `canonicalDatasetHash`로 해싱합니다. 그래서 두 원본 형식은
서로 다른 `sourceArtifactHash`와 `rawRowHash`를 유지하면서도 하나의 의미상
데이터셋과 재현 결과로 수렴할 수 있습니다. 허용되는 가격이나 수량 표기가 소수점
이하 끝자리 0에서만 다를 때에도 마찬가지입니다. 원본 행 해시는 고치지 않은 원본
문자열을 대상으로 하므로 서로 다르게 남습니다.

커밋된 네 행짜리 CSV와 JSON Lines 픽스처는 두 항목 연결 모두 `APPROVED`를
보고하고, 보호되는 15개 이벤트 항목 각각에 대해 4건 중 4건 일치를 보고합니다.
이것은 항목 단위 픽스처 점검이지 정확도 추정이 아닙니다. 이 문서가 들어 있는
커밋에서 `pnpm test -- packages/replay-engine/src/source-ingest.test.ts`로
재현하세요. 기록된 환경은 Node 22.18.0, pnpm 10.33.2, Vitest 4.1.11, Linux WSL2
x86_64입니다. 표본은 같은 네 이벤트를 담은, 직접 작성한 완전한 합성 형식 두
개이며, 독립된 자료나 운영 자료에서의 성능을 측정하지 않습니다.

이와 별개로, 사례 재현 따라가기는 서버에서만 도는 결정론적 픽스처 항목 연결
공급자를 실행합니다. 그 제안은 정확한 원본 아티팩트 해시로 찾아지고, 원본 열,
목표 항목, 변환, 확신도, 근거, 제안 상태를 드러냅니다. 픽스처 공급자는 어떤
네트워크 호출도 하지 않고 인증 정보도 쓰지 않습니다. 명시적으로 켠 설정 공급자는
검토자가 요청했을 때 커밋된 두 합성 형식에 대해 대신 항목 연결을 제안할 수
있습니다. 앞 여덟 행이라는 표본은 커밋된 위치만으로 정해집니다. 열과 칸의
텍스트는 자료로만 다루고, 응답은 엄격하게 검증되며, 확신도가 낮거나 모호한
출력은 거부되고, 검증된 그 제안이 사람의 승인과 재현을 위해 수명이 짧은 암호화된
영수증에 묶입니다. 이는 의미상의 정확도나 공급자 품질을 뒷받침하지 않으며,
시험은 통신 계층을 모의합니다.
[ADR 0029](adr/0029-bind-configured-mapping-proposals-to-review.md)(영문)를
참고하세요.

기본 픽스처 모드에서 두 형식 모두 선언된 항목을 만들어 냅니다. 형식 A는 끝까지
해석됩니다. 형식 B의 `source_note`는 목표와 변환이 없는 상태로 확신도 `0`의
`REVIEW_REQUIRED`로 판단을 요청합니다. 검토자가 그 항목 재정의에 빈칸이 아닌
사유를 적기 전에는 사례 재현 화면이 그 제안에 대한 승인을 만들지 않습니다.
승인은 불투명한 로컬 참조 `reviewer:local-lab`을 씁니다. 권한은 서버에 있습니다.
서버가 그 제안을 독립적으로 해싱하고, 사유가 적힌 재정의를 검증하고, 실행 가능한
유일한 항목 연결을 거기서 만들어 냅니다. 제안 상태만으로는 결코 승인이 되지
않습니다. 재정의는 승인 메타데이터를 바꿀 뿐 승인된 항목 연결의 투영을 바꾸지
않으므로 정본 결과 해시는 그대로입니다. 브라우저의 항목 연결 승인과 사례 승인은
서버가 쓰는 것과 같은, 런타임에 중립인 정본 직렬화기로 직렬화된 뒤 Web Crypto가
SHA-256을 계산합니다. 정본화나 해싱을 할 수 없거나 실패하면 사례 재현 화면은
승인 해시 오류를 표시하고, 승인을 만들지 않으며, 재현을 막아 둡니다.

### 사례 해석

시작 동작은 `/replay?mode=guided`를 열며, `/replay` 자체도 같은 따라가기를
엽니다. 직접 조작은 그 옆에 이름이 붙은 대안입니다. 각 단계는 무엇을 보여
주는지, 넘어가려면 무엇을 해야 하는지, 그리고 그 단계에서 한 일을 모델이
제안했는지 사람이 승인했는지 버전이 고정된 코드가 판정했는지를 밝힙니다.
어느 단계든 열어서 읽을 수 있고, 완료는 방문자가 실제로 충족한 단계에만
기록되며, 이후의 변경으로 더 이상 충족되지 않으면 회수됩니다. `SUPPORTED`
사례와 형식 B 검토 예시는 서로 다른 커밋 원본이고, 제안 해시와 승인이
독립적입니다. 예시에서 연결되지 않은 항목은 사유와 함께 남으며, 이것이 변환을
지어내거나 규칙 매니페스트를 제공하지는 않습니다. 본 사례에는 자체적인 명시적
항목 연결 승인과 사례 승인이 필요합니다.

따라가기는 실제 원본 문자열과 좌표, 픽스처 제안의 항목들, 승인 기록, 작성된 사례
범위와 기준값, API가 돌려준 판단 항목과 원본 추적을 보여 줍니다. 평가와 원본
추적을 갖춘 `REPLAYED`만 완료된 사례로 셉니다. 기반 응답은 규칙 결과가 아닙니다.
바뀌지 않은 승인 사례를 다시 실행하면 돌려받은 두 해시를 문자열로 비교하며,
브라우저에서 지표를 계산하거나 증거를 다시 연결하지 않습니다.

## `RAPID_PRICE_LIFT` 버전 `1.1`

이벤트가 적격이 되려면 종목이 승인된 가설과 일치하고, 종류가 `TRADE`이고,
부호 있는 나노초 이벤트 시각이 승인된 구간 안(양 끝 포함)에 있고, `price`,
`quantity`, `side`, `actorId`가 모두 있으며 `price`와 `quantity`가 둘 다 엄격히
양수여야 합니다. 이 규칙 입력 가운데 하나라도 없거나 `price` 또는 `quantity`가
양수가 아닌 체결은 `nonComparableEventCount`를 늘리고 어떤 지표에도 들어가지
않습니다. 적격 이벤트는 정본 `eventTime -> sequence -> eventId` 순서를
유지합니다.

| 지표                                  | 정의                                                       |
| ------------------------------------- | ---------------------------------------------------------- |
| `referencePrice`                      | 첫 적격 이벤트의 가격                                      |
| `peakPrice`                           | 적격 가격 가운데 최댓값                                    |
| `priceChangeBps`                      | `(peakPrice - referencePrice) * 10000 / referencePrice`    |
| `aggressiveBuyNotional`               | 적격 `BUY` 이벤트의 `price * quantity` 합                  |
| `totalNotional`                       | 모든 적격 이벤트의 `price * quantity` 합                   |
| `aggressiveBuyShareBps`               | `aggressiveBuyNotional * 10000 / totalNotional`            |
| `approvedActorBuyNotional`            | 승인된 집단에 속한 거래 주체의 적격 매수 금액              |
| `actorConcentrationShareBps`          | `approvedActorBuyNotional * 10000 / aggressiveBuyNotional` |
| `executionsAboveReference`            | 기준가보다 높은 가격의 승인 주체 `BUY` 건수                |
| `priceChangeBpsWithoutApprovedActors` | 승인된 거래 주체 집단을 제거하고 다시 계산한 가격 변화     |
| `removalSensitivityBps`               | `priceChangeBps - priceChangeBpsWithoutApprovedActors`     |

제거는 남은 적격 이벤트에서 기준가와 최고가를 모두 다시 계산합니다. 승인된
매니페스트가 지목한 거래 주체 집단만 제거합니다.

| 판단 항목              | 정확한 조건                                                       |
| ---------------------- | ----------------------------------------------------------------- |
| `PRICE_CHANGE`         | `priceChangeBps >= minimumPriceChangeBps`                         |
| `AGGRESSIVE_BUY_SHARE` | `aggressiveBuyShareBps >= minimumAggressiveBuyShareBps`           |
| `ACTOR_CONCENTRATION`  | `actorConcentrationShareBps >= minimumActorConcentrationShareBps` |
| `REPEATED_EXECUTION`   | `executionsAboveReference >= minimumExecutionsAboveReference`     |
| `REMOVAL_SENSITIVITY`  | `removalSensitivityBps >= minimumRemovalSensitivityBps`           |

비율 `a / b`와 소수 기준값 `t`에 대해, 엔진은 공통 배율의 정수 교차곱을
비교합니다. 표시용으로 계산된 몫을 비교하는 일은 없습니다. 베이시스포인트 값은
보고할 때만 소수점 넷째 자리까지 0 방향으로 버립니다. 개수는 부호 없는 정수
문자열입니다. 따라서 표시된 값이 기준값과 같아 보여도 정확한 값이 더 낮으면
충족하지 못할 수 있습니다.

모든 적격 이벤트의 가격과 수량이 엄격히 양수이므로, 기준가·총 거래대금·잔존
기준가가 양수인지에 대한 확인은 별도의 전제 조건으로 드러나지 않고 적격성으로
보장됩니다. 남은 전제 조건은 다음 순서로 실행되며 첫 실패에서 멈춥니다.

| 전제 조건                          | `INCONCLUSIVE` 사유                  |
| ---------------------------------- | ------------------------------------ |
| 적격 이벤트가 둘 이상              | `INSUFFICIENT_ELIGIBLE_EVENTS`       |
| 적극 매수 금액이 양수              | `NO_AGGRESSIVE_BUY_NOTIONAL`         |
| 거래 주체 제거 후 이벤트가 둘 이상 | `REMOVAL_LEAVES_INSUFFICIENT_EVENTS` |

전제 조건을 모두 통과한 뒤 다섯 판단 항목이 모두 충족되면 `SUPPORTED`,
하나라도 충족하지 못하면 `NOT_SUPPORTED`입니다. 각 발견은 관측된 문자열, 설정된
기준값, 충족 여부, 그리고 비어 있지 않은 정본 이벤트 참조를 담습니다.

## `CROSS_MARKET_SESSION_REVERSAL` 버전 `1.0`

거래 주체가 없는 이 규칙은 선언된 `analysedDate` 하나를 평가합니다. 후보 날짜를
찾기 위해 기준선을 훑지 않습니다. 승인된 매개변수는 양 끝을 포함하는
`baselineRange`, `baselineLegId`, 서로 다른 종목 구간 둘 이상, 각 구간의 최소
되돌림 배수, 최대 기준선 순위, 최소 동조 구간 수를 지목합니다. 설정된 모든
종목은 사례 매니페스트 `1.4`의 종목 집합과 정본 데이터셋 프로파일에도 있어야
합니다.

이벤트 `1.3`은 발행처의 시가, 고가, 저가, 종가와 전일 대비 변화의 절댓값을 정본
소수 문자열로 유지합니다. 하루의 관측값마다 다음을 계산합니다.

| 관측값      | 정확한 정의                                                                           |
| ----------- | ------------------------------------------------------------------------------------- |
| 세션 방향   | `closePrice - openPrice`의 부호                                                       |
| 세션 되돌림 | 하락 세션은 `highPrice - closePrice`, 상승 세션은 `closePrice - lowPrice`, 보합이면 0 |
| 순변화 방향 | 발행된 `netChange` 절댓값 항목의 부호                                                 |
| 관계        | 두 방향에서 나오는 `OPPOSED`, `ALIGNED`, `FLAT`                                       |
| 되돌림 배수 | `sessionReversal / abs(netChange)`                                                    |

엔진은 발행처가 반올림한 변화율에서 순변화를 유도하지 않습니다. OHLC 값이 양수인지,
그리고 `low <= open, close <= high`인지 검증합니다. 모든 가격·기준값·비율 비교는
확대된 정수와 정확한 교차곱을 쓰며, 보고되는 배수는 판단 항목이 결정된 뒤에만
소수점 넷째 자리까지 0 방향으로 버립니다.

기준선 모집단은 선언된 기준선 구간과 승인된 사례 매니페스트 시간 창이 겹치는
범위 안에서 비교 가능한 기준선 구간 관측값입니다. 그 사례 창 밖의 이벤트는 결과에
영향을 줄 수 없습니다. 분석 대상일의 순위는 `1 + count(배수 > 분석일 배수)`이고,
값이 같으면 순위를 공유합니다. 결과는 그 위치와 모집단 크기를 문자 그대로의 해석
`POSITION_WITHIN_DECLARED_RANGE_NOT_PROBABILITY`와 함께 보고합니다. 순위는 선언된
구간 안에서의 위치이지 확률이 아닙니다.

`BASELINE_RANK` 발견은 설정된 위치 이내일 때, 즉 순위가
`maximumBaselineRank`보다 크지 않을 때 충족됩니다. 선언된 각 구간은 별도의
`LEG_REVERSAL_MULTIPLE` 발견을 가지며, 관계가 `OPPOSED`이고 정확한 배수가 그
구간의 기준값 이상일 때만 충족됩니다. `AGREEING_LEGS`는 그렇게 충족된 구간
판단을 셉니다. `SUPPORTED`가 되려면 순위와 동조 구간 판단이 충족되어야 하고,
그 밖의 조합은 `NOT_SUPPORTED`입니다. 모든 판단 항목이 관측값, 기준값, 충족 여부,
정본 이벤트 참조를 보고하므로, 설정된 정족수 덕분에 결과가 충족되더라도 충족되지
못한 구간은 그대로 보입니다.

전제 조건은 명시적인 사유와 함께 `INCONCLUSIVE`로 닫힌 실패를 합니다. 그 어휘는
비교 가능한 기준선이 비었거나 하루뿐인 경우, 분석 대상일이 구간 밖이거나
기준선에 없는 경우, 선언된 구간이 없는 경우, 관측이 모호한 경우, OHLC 값이
불완전하거나 유효하지 않은 경우, 분석일의 순변화가 0인 경우를 다룹니다.
`INCONCLUSIVE` 결과에는 발견도 분석 내용도 없습니다.

커밋된 공개 자료 회귀 정답 기록은 양 끝을 포함하는 2026-07-01–2026-09-03 코스피
200 기준선 위에서 2026-09-03을 선언하고, 코스피 200과 2026년 9월 최근월 선물을
구간으로 둡니다. 기준선 구간은 `13.9147`과 `45` 중 `1`번째 위치를, 선물 구간은
`25.4705`를 보고하며, `SUPPORTED` 결과 해시는
`ffd7110a1c1fb2b18e9200e3a103b03572cb5b97b5f5d6db81689821de63bb55`입니다.
재현 명령은 다음과 같습니다.

```bash
pnpm exec vitest run packages/replay-engine/src/cross-market-session-reversal.test.ts
```

기록된 환경은 Node 22.18.0, pnpm 10.33.2, Linux WSL2 x86_64입니다. 이것은 고정된
라이선스 아티팩트에 대한 결정론적 엔진 회귀 점검입니다. 여기서 생성한 승인
픽스처는 해시 관문을 통과시키기 위한 것이며 사람의 검토를 증명하지 않으므로, 이
정답 기록은 승인된 사례도 증거로서의 결과도 아닙니다. 별도의 공개 웹 사례는
실행 전에 정확한 범위에 묶인 `APPROVED` 기록을 요구하고, 모든 판단 항목을 그
기준값의 출처로 되짚어 줍니다. 서버는 검토자의 신원을 인증하지 않습니다. 두
경로 모두 탐지 품질, 확률, 인과, 법적 지위, 투자 적합성을 추정하지 않으며,
구간에서 후보 날짜를 찾지도 않습니다.

## 판단 보류

필요한 식별자, 시각, 매매 방향, 가격, 수량, 항목 연결을 확정할 수 없으면
`INCONCLUSIVE`나 `REVIEW_REQUIRED`를 돌려주어야 합니다. 안전에 중요한 값이 빠졌을
때 모델의 추측으로 채워서는 안 됩니다.

## 합성 데이터

합성 픽스처는 세 결과 상태에 모두 도달하며, 실제 시장에서의 성능을 추정하지 않고
계약, 실패 처리, 결정성, 추적 가능성을 시험합니다. 이와 별개로, 커밋된 공개
코스피 200 기준선과 최근월 선물 행이 하나의 `SUPPORTED` 엔진 출력을 고정합니다.
그 정답 기록은 결정론적 회귀 증거이지, 사람이 승인한 사례도, 성능 추정도, 일반적인
탐지 주장도 아닙니다. 공개 웹 사례는
[ADR 0034](adr/0034-evaluate-real-instruments-without-altering-source-facts.md)(영문)에
적힌 승인·공개 안전장치를 적용합니다.
